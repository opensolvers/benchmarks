----- Recommendation -----
Prefer plain SoA + GCC -ftree-vectorize over hand walberla::simd::double4_t
for this collide pattern on RVV/GCC 14. Fixed VL=4 simd underperforms scalable
auto-vec here. FORCE_SCALAR previously looked "fast" only relative to spill-y
simd; unwrapped double* SoA is much faster still.

----- App-level (CellwiseSweep / SplitPureSweep) -----
No small safe patch applied. Blockers for auto-vec in full LBM sweeps:
1. CellwiseSweep: per-cell filter + Field::get(x±Δ,y±Δ,z,f) pull stencil —
   non-contiguous neighbor gathers; XYZ iterator with ghost padding.
2. Stream-collide pull (D2Q9): 8 of 9 directions read off-x-line (y±1);
   even with fzyx SoA, y-neighbor PDF rows are not contiguous with the
   current x-row for auto-vec of the fused stream-collide.
3. SplitPureSweep already uses WALBERLA_RESTRICT temps and x-loops, but
   still routes PDF I/O through Field::get with neighbor offsets — same
   gather problem for streaming directions.
4. Collide-only (no stream) on contiguous f-component rows is what this
   microbench proves vectorizes; that is NOT the default 01_BasicLBM path.
